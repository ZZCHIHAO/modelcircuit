阶段编号表示开发顺序，版本号为建议。各阶段按独立验收拆成版本 PR。疑难任务可先用一个小模型和一份已知答案的样本验证契约，再扩大到真实输入和更多模型。进度取决于可用的测试数据、GPU 和环境条件。

保留原生桌面入口和现有正交接线。基础组件库、深度学习模型库、传统机器学习模型库、网络结构与融合库、任务和数据适配组件围绕当前图与组件注册接口扩展。模型组件展示输入格式、输出端口、权重来源和可执行能力。展开式 ResNet、ViT 与分割起始图可继续编辑。ConvNeXt、Swin 等新增模型先为明确的任务实现接口、权重和端口测试，公开扩展方式供其他模型注册。实际运行的模型容量按设备资源检查，批次约束和文件解析边界单独管理。

## 任务扩展与 1.0 验收范围

工作区继续用同一份图表示描述端口、调用关系、参数共享和芯片层级。实验工程在图外记录任务、数据、执行配置和产物。PyTorch 训练采用前向、损失、反向和参数更新。传统 ML 按拟合、交叉验证和预测执行。生成与检索按查询、检索、生成和评价执行。三类任务在桌面共享工程管理和结果入口。

组件和任务扩展应声明版本、具名端口、参数、预处理、支持的运行环境和输出产物。候选版应能通过公开接口注册一个未内置的模型组件和一个示例任务适配器，并证明安装、校验、运行、导出和重开都能走正常流程。生成的 Python 提供可编辑的受支持区域，外部库与动态逻辑可封装为具名输入输出的代码组件。能恢复的结构以实际解析结果为准。

目标检测、时序预测、音频和更多视频任务可沿接口展开。优先级取决于数据、评价方案和模型适配验证。正式版的支持矩阵按实际完成的工作流填写。本文把 1.0 设为平台与扩展接口的首个稳定版本，后续模型和任务可独立演进。

## S10 执行清单

**最小交付场景** 研究者在桌面保存一次三维分割实验，导出工程，把工程复制到另一台机器并指定共享数据目录。运行 Python 入口后得到可打开的训练报告和掩码，再把支持的 Python 模型修改重新导入画布。二维分类作为第二个任务复用相同工程接口。

1. [ ] **定义工程清单与兼容边界。** 从 `studio/native/workspace_state.py` 的 JSON 保存和 `studio/backend/studio_core/experiment_spec.py` 的身份校验出发，定义清单版本、图快照、任务、组件版本、配置、环境和可选权重。给历史 `run_spec.json`、工作区及 checkpoint 保留原有加载规则。验收用 S8 和 S9 的工作区、权重及预测产物。
2. [ ] **实现数据重绑。** 对受支持数据记录逻辑根目录、相对路径、内容摘要、预处理和划分。绝对本地路径依然用于当前机器寻找文件。搬迁时用相对路径和摘要逐项核对数据，拒绝内容已变的同名文件。既有 `dataset_digest` 和检查点签名继续用于历史运行。迁移运行产生新快照，记录源运行和已核对的数据来源。在 S10 首批场景用新路径启动实验，跨路径续训需额外验证优化器、随机状态和批次的恢复后再启用。
3. [ ] **导出独立运行的 Python 工程。** 建议内容为 `model.py`、`experiment.json`、运行入口、依赖声明和数据清单。分享时用逻辑路径引用数据，由接收者重绑本地数据。权重随工程交付时记录来源、格式和摘要。沿用 `python_io.py` 建模，共享 `classification_runtime.py` 和 `segmentation_inference.py` 的任务规则。独立启动的验收在项目源码目录之外的干净 Python 环境进行。按工程内的依赖声明安装后，通过同一入口启动训练和推理。依赖分为通用和硬件相关部分，启动时显示最终设备与版本。
4. [ ] **实现图与代码回写。** 在支持的语法内，以静态解析得到的模型结构为准。布局和稳定身份可在语义匹配后恢复。代码新增或修改连接及参数时，把变化反映到图中并重新校验。无法解析的局部给出文件和位置，并保留原始代码。验证修改一处卷积参数和一条共享分支，分别测试正常修改、形状冲突及过时布局信息。
5. [ ] **接入桌面工程和历史。** 增加「导出实验工程」「重新绑定数据」「打开运行结果」。首次运行提供可直接打开的示例工程，界面按选数据、连模型、检查端口、选设备、运行的顺序提示当前缺项。历史页显示运行时使用的模型版本、任务、划分、设备、种子和主要指标。指标定义、划分及评价协议匹配时提供同图对照。查看结果时支持定位到 checkpoint、日志、预测、探针和源画布。
6. [ ] **验收和交付。** 用合成二维分类和三维分割跑通导出、迁移、CPU 重跑、代码回写、报告重开。按预先记录的容差核对前向、训练步和产物，另测试缺数据、错误权重、失配代码和旧工程打开。对统一 Windows EXE 做程序化验收，提交含版本号和验证结果的 PR。

## 影响排期的技术决定

- **多卡。** PyTorch 2.6 官方资料将 DDP 作为优先路径。该版本记录的 Windows 分布式支持不含 NCCL，因此把 Linux DDP 作为第一条多卡验收路线。Windows 的 DP 选项只有在针对现有任务的两卡测试通过后才开放。能力展示应取自当前运行环境，并显示卡号、每卡批次和原因。来源见 [PyTorch 2.6 Distributed](https://docs.pytorch.org/docs/2.6/distributed.html)、[torchrun](https://docs.pytorch.org/docs/2.6/elastic/run.html) 和 [DataParallel](https://docs.pytorch.org/docs/2.6/generated/torch.nn.DataParallel.html)。
- **指标。** 分类、分割、传统 ML 和生成以同一工程接口记录实验，但由各自的任务适配器定义动作和评价。数据预处理与特征选择要在训练数据内拟合。比较多模型时固定划分、预处理和指标定义。来源见 [scikit-learn 常见问题](https://scikit-learn.org/stable/common_pitfalls.html)。
- **兼容性。** 每次调整图、工作区、数据清单或后端能力时提供旧版样例。预测和评估可用小型输入按固定随机种子核对，CPU 与 CUDA 分别明确可接受的数值误差。支持范围以实际测试记录为准。

外部资料核查日期为 2026 年 11 月 19 日。功能、版本和验收条件属于研发计划。真实三维数据和两卡训练的验收安排依赖可用数据与硬件。
